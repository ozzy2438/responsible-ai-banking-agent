# Synthetic Data

All customer, account, and transaction data in this repository is synthetic.
`customers.synthetic` is database-enforced (`CHECK (synthetic)`); nothing here
represents a real person or a real bank's records — see the
[system card](system-card.md) and [privacy and data lifecycle](privacy-data-lifecycle.md).

## Bulk seed migration

`migrations/0003_synthetic_seed_data.sql` seeds a larger population than the
two illustrative rows in `migrations/0001_schema.sql` (Alice/Bob), for local
development, demos, and stress-testing the deterministic control layer at
scale:

- 305 customers, 358 accounts, 6,475 transactions (including the two existing
  Alice/Bob rows and their accounts/transactions).
- Applies automatically as part of the normal `make migrate` /
  `banking-agent-migrate` flow — no separate step.
- Every timestamp is a SQL `now() - interval '...'` expression, not a literal
  computed date, so seeded data stays fresh relative to whenever the migration
  is actually applied, matching the pattern already used in `0001_schema.sql`.

Generated by `scripts/generate_synthetic_seed.py`, a stdlib-only, dev-only
script (not part of the installed package). Re-running it produces
byte-identical output: all randomness comes from `random.Random(424242)`, and
every row ID is `uuid.uuid5` derived from a fixed namespace, so nothing depends
on wall-clock time or process entropy. Regenerate with:

```sh
.venv/bin/python scripts/generate_synthetic_seed.py > migrations/0003_synthetic_seed_data.sql
```

Once `0003_synthetic_seed_data.sql` has been applied anywhere, treat it as
immutable like any other migration — `migrate()` hash-checks applied
migrations and raises if a previously applied file changes. A future change
to the seed data is a new numbered migration (for example, `0006_...`), not
an edit to `0003`.

being part of the randomly generated population, so tests and demos can refer

## Extended scenario corpus

`evaluation/synthetic_scenarios.json` is a separate, wider set of request
scenarios (30 cases) that reference the fixtures above and a few of the
randomly generated customers, run end-to-end against the real
Postgres-backed `Repository` by `tests/integration/test_synthetic_scenarios.py`.

This is **not** the blocking release gate. `evaluation/golden_cases.json`
(48 fixed cases, exact category counts asserted by
`tests/evaluation/test_golden_cases.py`, thresholds documented in
[the evaluation rubric](evaluation-rubric.md)) remains the blocking corpus and
is untouched by this work. The extended corpus exists to prove the same risk
taxonomy holds against real, varied, database-backed data — multiple
customers, multiple currencies, stale data, cross-customer access attempts —
rather than the golden suite's in-memory fake repository.

## What this does and does not do

This strengthens engineering confidence (access control, staleness handling,
citation generation) and demo quality at a realistic scale. It does not
replace [Stage 3 of the production readiness roadmap](production-readiness-roadmap.md)
— approved, real bank system and data integrations. A larger synthetic
dataset is still synthetic.
